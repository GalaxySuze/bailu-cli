# 白鹿 SDD D1 - 任务分配与评估

## 阶段入口契约

### 前置条件

1. `.sdd/sdd-context.md` 当前阶段为 `D1`，或该文件不存在（首次启动 SDD 流程）
2. 需求输入至少具备以下之一：
   - HTML 原型文件路径
   - MD 需求文档路径
   - 一句话需求描述

### 输入产物

| 输入项 | 来源 | 是否必须 |
|--------|------|----------|
| 需求描述（HTML/MD/文本） | 用户提供 | 是 |
| 项目工程目录 | git rev-parse --show-toplevel | 是 |
| 执行者 | git config user.name | 是 |

### 输出产物

| 输出项 | 路径 | 说明 |
|--------|------|------|
| 任务清单（Markdown 表格） | 对话中输出 | 可同步至 Teambition |
| sdd-context.md（更新） | `.sdd/sdd-context.md` | 阶段推进至 D2 |
| SP 汇总 | 对话中输出 | 按执行者汇总 |
| OpenSpec 任务清单（条件生成） | `openspec/changes/<change-name>/tasks.md` | 中等/大需求时生成 |

---

## 概述

引导研发完成需求的任务拆解、工作量估算和排期，最终输出可直接填入 Teambition 的任务清单（公司开发场景），或直接作为个人开发任务跟踪（个人开发场景）。完成后更新 `.sdd/sdd-context.md` 进入 D2 阶段。

## Step 1：获取需求输入

需求输入可能有以下形式，灵活处理，不要要求用户补充不必要的信息：

| 输入形式 | 处理方式 |
|----------|----------|
| HTML 原型文件路径 | 读取文件，提取页面结构和交互说明 |
| MD 需求文档路径 | 读取文件，提取功能点和验收标准 |
| HTML + MD 同时提供 | 两者结合分析，MD 优先作为需求说明 |
| 一句话需求描述 | 基于描述推断任务，估算时主动说明假设 |

读取完成后，直接进入任务拆解，若理解有偏差用户可在看到任务清单后指出。

## Step 2：获取执行者

执行 `git config user.name` 获取当前用户作为执行者，无需询问。

## Step 3：代码扫描辅助规模判定

**目的：在任务拆解前，通过自动扫描项目文件，辅助判定需求规模（涉及文件数、接口变更数），为后续 SP 估算和 OpenSpec 生成决策提供数据支撑。**

### 3.1 扫描项目结构

根据需求描述中的关键词，在项目目录中搜索相关文件：

```bash
# 示例：搜索与需求相关的后端文件
grep -rl "<需求关键词>" --include="*.java" --include="*.php" --include="*.py" --include="*.ts" --include="*.go" .
```

### 3.2 生成规模判定报告

根据扫描结果，输出规模判定摘要：

```
📊 代码扫描规模判定

涉及文件数：{N} 个
  - 后端：{N} 个文件（新增 {X} / 修改 {Y}）
  - 前端：{N} 个文件（新增 {X} / 修改 {Y}）
  - 数据库：{N} 张表（新增 {X} / 修改 {Y}）
接口变更数：{N} 个（新增 {X} / 修改 {Y}）

规模判定：{小需求 / 中等需求 / 大需求}
```

### 3.3 规模判定规则

| 涉及文件数 | 接口变更数 | 规模判定 | 后续流程 |
|-----------|-----------|----------|----------|
| ≤ 3 个 | ≤ 1 个 | 小需求 | D1 → D4（跳过 D2/D3） |
| 4 ~ 10 个 | 2 ~ 5 个 | 中等需求 | D1 → D2 → D3（AI 自检模式）→ D4 |
| > 10 个 | > 5 个 | 大需求 | D1 → D2 → D3（正式评审会模式）→ D4 |

规模判定结果将在 Step 6（OpenSpec 使用时机判断）中使用，并记录到 `sdd-context.md` 的 `需求规模` 字段中。

## Step 4：任务拆解

基于需求内容，按技术方向拆解开发任务。拆解原则：

- 每个任务对应一个可独立交付的功能单元（一个接口、一个页面、一个数据库改动等）
- 跨端任务分开拆（前端和后端分别是独立任务，不合并）
- 公共/基础工作单独列出（数据库建表、接口契约定义等）
- 任务粒度：1~5 SP 为宜；超过 5 SP 的建议拆分；0.5 SP 以下的合并
- 结合 Step 3 的代码扫描结果，对涉及文件较多的模块适当细化拆解

读取 SP 字典参考：`references/sp-dictionary.md`

每条任务输出格式：

```
序号 | 任务名称 | 模块 | 执行者 | SP | 截止时间
```

截止时间先留空（`—`），Step 5 统一处理排期。

拆解完成后展示完整任务列表，用户可直接告知调整意见，AI 修改后重新输出。

## Step 5：输出任务清单

确认后输出以下两份内容：

截止时间列保留为 `—`，由开发负责人后续根据实际人力、优先级和项目节奏填写（公司开发场景可在 Teambition 中填写，个人开发场景自行管理）。

### 5.1 任务清单（Markdown 表格）

```markdown
## 需求：{需求名称}
**需求编号**：{需求编号}  **SP总计**：{X} SP  **执行人**：{姓名}

| 序号 | 任务名称 | 模块 | 执行者 | SP | 截止时间 |
|------|----------|------|--------|----|----------|
| 1    | ...      | 后端 | 张三   | 3  | —        |
| 2    | ...      | 前端 | 李四   | 2  | —        |
```

并附一句提示：

**公司开发场景**（有 Teambition 使用习惯）：
```
✅ 以上内容可同步至 Teambition，建议以需求编号为父任务，每行为一个子任务。
```

**个人开发场景**：
```
✅ 以上任务清单可直接作为个人开发跟踪使用，无需同步至 Teambition。
```

> 提示方式：根据用户上下文判断场景类型，若不确定则默认展示公司开发场景的 Teambition 提示，同时补充"个人开发可跳过此步骤"。

### 5.2 SP 汇总

```
SP 总计：X SP
需求规模：{小需求 / 中等需求 / 大需求}（来自 Step 3 规模判定）
按执行者：张三 X SP / 李四 X SP
```

## Step 6：OpenSpec 使用时机判断

**目的：根据需求规模判定是否需要生成 OpenSpec 文档，为后续阶段提供结构化产物。**

### 6.1 判断规则

| 需求规模 | OpenSpec 是否需要 | 说明 |
|----------|-------------------|------|
| 小需求 | 不需要 | 直接进入 D4 编码，无需生成 OpenSpec artifacts |
| 中等需求 | 推荐生成 | 生成 `tasks.md`，供 D2 技术方案设计使用 |
| 大需求 | 必须生成 | 完整 OpenSpec 流程，D2 阶段将基于此生成 proposal.md/design.md/tasks.md |

### 6.2 执行逻辑

- **小需求**：跳过 OpenSpec 生成，直接推进至 D4，提示"需求规模较小，跳过 OpenSpec 文档生成，直接进入编码阶段"
- **中等需求 / 大需求**：创建 `openspec/changes/<change-name>/` 目录，生成初始 `tasks.md`（与 D1 任务清单对齐）

> `change-name` 从需求编号 + 需求名称自动派生 kebab-case 命名。

### 6.3 生成的 tasks.md 格式

```markdown
# 开发任务清单 - {需求名称}

**需求编号**：{需求编号}
**SP总计**：{X} SP
**需求规模**：{中等需求 / 大需求}

## 任务列表

| 序号 | 任务名称 | 模块 | 执行者 | SP | 状态 |
|------|----------|------|--------|----|------|
| 1    | ...      | 后端 | 张三   | 3  | 待开始 |
| 2    | ...      | 前端 | 李四   | 2  | 待开始 |
```

## Step 7：更新 SDD 上下文

读取项目根目录 `.sdd/sdd-context.md`，更新以下字段：

```bash
GIT_USER=$(git config user.name)
PROJECT=$(basename $(git rev-parse --show-toplevel))
```

| 字段 | 更新值 |
|------|--------|
| 需求编号 | 用户确认的需求编号（若未提供，询问） |
| 需求名称 | 从需求文档提取的需求名称 |
| 当前阶段 | D2 |
| 需求规模 | 来自 Step 3 规模判定（小需求 / 中等需求 / 大需求） |
| SP总计 | 本次估算的 SP 汇总 |
| 执行人 | git config user.name |
| 工程名 | basename of git root |
| D1产物 | openspec/changes/{change-name}/tasks.md（中等/大需求时填写，小需求标注"跳过"） |

> **严格遵守**：只更新以上字段，禁止写入需求背景、任务描述或任何其他内容。格式规范见根 SKILL.md 的「sdd-context.md 格式规范」章节。

更新完成后，输出进度块（按根 SKILL.md 的进度块规则，D1 标 ✅，D2 标 ▶️），然后提示：

```
✅ D1 完成！sdd-context.md 已推进至 D2
直接说"继续"或"开始技术方案"即可。
```

## 边界与注意事项

- 若用户只提供一句话需求，估算时主动说明你的假设，让用户有机会纠正
- 不要自行决定"这个任务不需要估算"，所有任务都要给 SP 建议
- SP 字典是参考，用户可以覆盖，以用户最终确认的 SP 为准
- 截止时间不考虑节假日，如用户提到节假日则手动调整工作日
- 执行者统一取 git config user.name，不询问
- Teambition 同步为选填项：公司开发场景建议同步，个人开发场景可跳过
- 代码扫描结果仅作为规模判定参考，不替代人工判断
- OpenSpec 生成时机由规模判定结果决定，小需求不生成以减少流程开销
