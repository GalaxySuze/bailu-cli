# 白鹿开发工作流规则

## 核心原则

1. **SDD 为默认引擎**：使用 SDD 七阶段研发管理（D1→D7），白鹿原生四阶段为 Fallback
2. **阶段推进**：严格按照 D1→D2→D3→D4→D5→D6→D7 推进研发任务（根据规模可跳过部分阶段）
3. **人工节点**：每个阶段的关键决策点需用户确认后方可继续
4. **状态持久化**：研发状态通过 `.sdd/sdd-context.md` 管理，支持断点恢复和多需求并行
5. **决策记录**：关键技术决策需记录在 ~/.bailu/knowledge-base/projects/{project}/decisions/ 目录下

## SDD 阶段说明

| 阶段 | 名称 | 主导 Agent | 核心产出 |
|------|------|-----------|---------|
| D1 | 任务分配与评估 | planner | 任务清单 + SP 汇总 |
| D2 | 技术方案设计 | architect | proposal.md + design.md + tasks.md |
| D3 | 技术方案评审 | code-reviewer | review.md（通过/有条件通过/不通过） |
| D4 | 开发编码 | backend/frontend-developer | 代码实现 |
| D5 | 代码评审 | code-reviewer | AI 审核 + 人工审核记录 |
| D6 | 测试与缺陷闭环 | test-engineer | 测试记录 + 缺陷闭环 |
| D7 | 上线/发版（可选） | code-reviewer | MR + 发布清单 |

## 三级规模路由

- **小需求（快速模式）**：D1 → D4 → D5 → D6，跳过 D2/D3，预计 1-2 轮对话
- **中等需求（标准模式）**：D1 → D2 → D3(AI自检) → D4 → D5 → D6，预计 3-5 轮对话
- **大需求（完整模式）**：D1 → D2 → D3(正式评审会) → D4 → D5 → D6 → D7，预计多天多轮对话

### 规模自动判定

| 信号特征 | 推荐规模 |
|---------|---------|
| "加一个"、"改一下"、纯前端样式、无接口变更 | 小需求 |
| 有接口新增/变更、前后端协作、涉及多个模块 | 中等需求 |
| 新建系统/子系统、跨团队协作、改动量大 | 大需求 |
| 描述模糊、范围不清晰 | 中等需求（保守推荐） |

### 文件扫描辅助判定

| 扫描结果 | 推荐规模 |
|---------|---------|
| 涉及文件 ≤ 2 且无接口变更 | 小需求 |
| 涉及文件 3-5 或有 1-2 个接口变更 | 中等需求 |
| 涉及文件 > 5 或新建模块 | 大需求 |

## OpenSpec 使用时机

**需要 OpenSpec**：多文件功能开发（3+文件）、破坏性变更、需要设计决策、跨领域架构变更

**无需 OpenSpec**：简单 Bug 修复、微小调整、显而易见的重构、单行文字修改

## 阶段切换规则

### SDD 模式
- D1→D2：用户确认任务拆解后（小需求跳过直接进 D4）
- D2→D3：design.md 生成后（小需求跳过）
- D3→D4：评审通过或有条件通过后（不通过退回 D2）
- D4→D5：所有编码任务完成且验证通过后
- D5→D6：AI 审核 + 人工审核均通过后
- D6→D7：测试与缺陷闭环完成后（D7 可选）
- D7→完成：MR 创建 + 发布清单更新后

### Fallback 模式（白鹿原生四阶段）
- 阶段1→2：用户确认方案方向后
- 阶段2→3：用户确认架构和任务拆分后
- 阶段3→4：所有编码任务完成且用户确认 Review 后
- 阶段4→结束：用户最终验收后

## 开发规范

### 代码风格
- 遵循项目现有的代码规范和目录结构
- 新文件使用项目已有的命名约定
- 优先复用项目已有的工具函数和组件

### 质量要求
- 所有新增代码需包含必要的错误处理
- 关键逻辑需添加单元测试
- API 变更需更新接口文档
- 不引入安全漏洞（SQL注入、XSS、敏感信息泄露等）

### Git 提交规范
- 提交信息格式：`<type>(<scope>): <description>`
- type: feat / fix / docs / style / refactor / perf / test / chore
- 每次提交聚焦单一变更
- 提交前确保代码通过 lint 和测试

### 分支规范
- 格式：`{prefix}-{YYYYMMDD}-{type}-{需求编号}-{描述}-{git用户名}`
- type: task / bug / hotfix / feature / release
- 不符合规范时自动引导创建规范分支

## 工作流触发条件

以下关键词自动触发开发工作流：
- 开发、写代码、实现功能、添加特性
- bug、修复、debug、问题
- 重构、优化、改进
- API、接口、数据库、部署、测试
- 开始SDD、我要开发需求、开始研发（SDD 模式）
