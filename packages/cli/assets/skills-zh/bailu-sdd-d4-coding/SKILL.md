# SDD D4 - 开发编码

## 概述

AI 执行编码，人做审核与决策。

基于 D2 生成的 OpenSpec artifacts 和 D3 通过的评审，AI 按 `tasks.md` 逐任务自动实现代码变更，遇到关键决策点主动暂停询问，完成后推进至 D5 Code Review。

**D4 不做**：自行修改评审不通过的方案、跳过任务、绕过人工确认的关键风险点。

## 白鹿 Agent 协作模式

D4 编码阶段根据任务类型自动路由到对应的白鹿 Agent 执行：

- **后端任务**：由 `backend-developer` Agent 执行，负责服务端代码、数据库操作、API 接口、业务逻辑等
- **前端任务**：由 `frontend-developer` Agent 执行，负责页面组件、样式、交互逻辑、接口对接等

Agent 之间通过 OpenSpec artifacts（`design.md`、`tasks.md`）中的接口契约和字段定义保持协作一致性。

## 阶段入口契约

### 前置条件

进入 D4 编码阶段前，必须满足以下条件：

1. 当前阶段 = `D4`（读取 `.sdd/sdd-context.md` 确认）
2. 若为**小需求**：无需 D3 评审记录
3. 若为**中等/大需求**：D3 评审结论不等于"不通过"
4. 当前分支符合规范：`{prefix}-{YYYYMMDD}-{type}-{需求编号}-{desc}-{username}`

### 输入产物

- `.sdd/sdd-context.md` — SDD 上下文（需求编号、需求名称、当前阶段等）
- `openspec/changes/<change-name>/tasks.md` — 任务清单（中等/大需求）
- `openspec/changes/<change-name>/design.md` — 技术设计方案（中等/大需求）
- `openspec/changes/<change-name>/proposal.md` — 需求提案（中等/大需求）
- `openspec/changes/<change-name>/review.md` — D3 评审记录（若存在）

## Step 1：前置检查

### 1.0 判断需求规模

读取 `.sdd/sdd-context.md` 中的 `需求规模` 字段：

- **小需求**：跳过 1.2（评审结论检查），进入小需求模式（见 Step 2 小需求分支）
- **中等需求 / 大需求**：正常执行以下所有步骤

### 1.1 确认阶段合法

读取 `.sdd/sdd-context.md`，当前阶段必须为 `D4`。

若当前阶段为 `D2` 或 `D3`，停止并提示：

```
当前阶段为 {阶段}，D4 编码需要 D3 技术方案评审通过后才能执行。
请先完成 sdd-d3-tech-review。
```

### 1.2 检查评审结论

尝试读取 `openspec/changes/<change-name>/review.md`。

**文件不存在**（D3 被跳过）：提示风险后询问是否继续：

```
⚠️ 未找到 D3 评审记录，技术方案未经过评审。
是否仍然继续 D4 编码？(y/N)
```

用户确认后继续，不强制阻塞。

**文件存在**：确认最新一轮评审结论不是"不通过"。若为"不通过"，停止：

```
最新评审结论为"不通过"，请先完成方案修改并通过 D3 评审。
```

若为"有条件通过"，读取待跟踪项，在编码过程中主动关注这些项是否已在代码层落实，并在 Step 6 输出确认结果。

### 1.3 确认开发分支

执行：

```bash
git branch --show-current
```

检查当前分支是否符合规范：`{prefix}-{YYYYMMDD}-{type}-{需求编号}-{desc}-{username}`。

**不符合规范**：

读取 `bailu-sdd-d4-git-branch` skill，按其中流程引导用户创建规范分支。

**符合规范**：展示分支名，继续。

## Step 2：读取任务

### 小需求模式（需求规模 = 小需求）

不读取 OpenSpec artifacts，改为直接扫代码：

1. 根据 D1 输出的任务描述（或用户描述），扫描相关源码文件，锚定真实类名和方法签名
2. 在会话中输出改动范围确认块：

```
📋 改动范围确认

涉及文件：
  - {文件路径} — {改动说明}
  - ...

改动点：
  1. {具体改动，如：新增方法 exportExcel(...)，参数 ...}
  2. ...

不涉及：{明确不会动的部分，如：DB 改动、权限变更}

确认后开始写代码，有调整直接说：
```

3. **等待用户确认**，收到"没问题"/"继续"或类似回复后再动代码
4. 确认后跳转至 Step 3 直接执行，不需要 tasks.md

---

### 中等/大需求模式

```bash
command -v openspec &>/dev/null && echo "openspec_available" || echo "openspec_missing"
```

**有 CLI**：执行 apply 指令获取完整上下文：

```bash
openspec instructions apply --change "<change-name>" --json
```

若 CLI 报告 artifacts 缺失，停止并告知缺少哪些文件，不继续。

**没有 CLI**：直接读取本地 artifacts 文件：

```
openspec/changes/<change-name>/tasks.md
openspec/changes/<change-name>/design.md
openspec/changes/<change-name>/proposal.md
```

若文件不存在，停止并提示：

```
未找到 OpenSpec artifacts，请确认 D2 已完成。
预期路径：openspec/changes/<change-name>/tasks.md
```

两种方式效果等同，均以 `tasks.md` 的任务列表为执行依据。

### 2.2 展示任务进度

输出当前任务全貌：

```
📋 任务进度 - {需求名称}

已完成：{X} / {总计}
待执行：{列出所有未完成任务}

即将开始：{第一个未完成任务}
```

展示完成后直接开始执行第一个未完成任务。

## Step 3：逐任务执行

循环执行每个未完成任务，直到全部完成。

### 每个任务的执行节奏

1. **宣告任务**：输出正在执行哪个任务，来自 tasks.md 第几项
2. **最小化变更**：只改当前任务涉及的代码，不顺手重构不相关代码
3. **立即勾选**：任务完成后立刻将 `tasks.md` 中对应的 `- [ ]` 改为 `- [x]`
4. **变更摘要**：输出本次任务修改了哪些文件、改了什么

### 特殊任务类型处理

**DB 变更任务**：

从 design.md 提取 DDL，直接输出供研发参考，不询问执行确认（DDL 由研发自行在对应环境执行，AI 不介入数据库操作）：

```
📋 本任务包含以下 DDL 变更，请在对应环境手动执行：

{DDL 内容}
```

输出后继续执行后续代码任务，不等待用户回复。

**三方系统/MQ/Redis 接入任务**：

输出接入配置参数和关键注意事项，直接继续执行代码，不等待确认。

**前端任务**：

读取 `design.md` 中 UI 章节的接口契约和字段定义，按此实现，不自行假设字段名或接口路径。

**ABAP 任务**：

对于 ABAP 项目，按照 ABAP Clean Code 原则执行编码，注意遵循 SAP 系统的最佳实践和命名约定。

## Step 4：关键决策点暂停

遇到以下情况，**主动暂停**，不自行决策：

| 暂停场景 | 暂停提示 |
|----------|----------|
| design.md 描述与代码现状冲突 | 说明冲突点，列出两种处理方式，让人选择 |
| 任务描述不够清晰，有多种实现路径 | 列出可选方案和各自影响，等待决策 |
| 需要引入新的依赖包 | 说明引入原因和版本，确认后再添加 |
| 测试失败且原因超出当前任务范围 | 输出完整错误信息，不自行扩大修改范围 |
| 发现 design.md 存在遗漏或错误 | 指出问题，询问是修改 design.md 还是按现有理解实现 |

暂停格式：

```
⚠️  需要决策：{简述问题}

背景：{来自 design.md 或代码的具体上下文}

选项：
1. {方案A} — 影响：{...}
2. {方案B} — 影响：{...}

请选择或告诉我你的想法：
```

## Step 5：执行验证

所有任务完成后，根据项目类型自动运行验证：

```bash
# 尝试识别项目类型并运行对应命令
# Maven 项目
mvn test -q 2>/dev/null
# Gradle 项目
./gradlew test 2>/dev/null
# Node 项目
npm test 2>/dev/null
# 其他
```

若无法识别，询问：

```
请提供本地验证命令（如 mvn test / npm run test）：
```

验证失败时，输出完整错误，询问：

```
测试失败，是否需要我分析原因并修复？
1. 是，在当前任务范围内修复
2. 否，记录为 D6 自测问题，先推进 D5
```

## Step 6：D3 待跟踪项确认

若 D3 评审结论为"有条件通过"，在此步骤逐条确认待跟踪项是否已在代码中落实：

```
D3 评审有以下待跟踪项，请确认代码中是否已处理：

[高] 导出接口需要加限流
→ 请告知：已落实 / 未落实 / 不在本次范围
```

将确认结果追加记录到 `review.md`：

```markdown
### D4 待跟踪项落实确认

| 问题 | 状态 | 说明 |
|------|------|------|
| 导出接口加限流 | 已落实 | 使用 Guava RateLimiter，100次/秒 |
```

## Step 7：推进 D5

所有任务完成且验证通过后，更新 `.sdd/sdd-context.md`（只修改以下字段，禁止写入其他内容）：

```
当前阶段: D5
```

输出进度块（按根 SKILL.md 的进度块规则，D1-D4 标 ✅，D5 标 ▶️），然后输出：

```
✅ D4 编码完成

📊 任务完成：{X}/{X}
🌿 开发分支：{分支名}
📋 变更摘要：
   - 修改文件：{文件列表}
   - 新增文件：{文件列表}

直接说"继续"或"开始代码评审"即可。
```

## 边界与注意事项

- 严格按 tasks.md 任务逐个执行，不跳跃、不合并、不超范围修改
- 每完成一个任务立即更新 tasks.md checkbox，不批量更新
- 遇到设计缺陷不自行修改 design.md，先暂停询问
- DB 变更直接输出 DDL 供研发参考，不等待用户确认即继续后续代码
- 不自行决定引入新依赖，必须经过人工确认
- 有条件通过的待跟踪项必须在 Step 6 逐条确认，不能跳过
