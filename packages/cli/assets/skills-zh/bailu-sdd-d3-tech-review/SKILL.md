# 白鹿 SDD D3 - 技术方案评审

## 阶段入口契约

### 前置条件

1. `.sdd/sdd-context.md` 当前阶段为 `D3`
2. `design.md` 非空（`openspec/changes/<change-name>/design.md` 存在且有内容）
3. D2 产物齐全（proposal.md、design.md、tasks.md 均存在）

### 规模路由规则

| 需求规模 | D3 评审方式 | 说明 |
|----------|-------------|------|
| 小需求 | 跳过 D3 | 小需求不进入 D3 阶段，直接从 D1 跳转 D4 |
| 中等需求 | AI 自检模式 | 仅执行模式一（评审前自检），无需正式评审会 |
| 大需求 | 正式评审会模式 | 必须执行模式二（评审会后记录），保留正式评审记录 |

### 输入产物

| 输入项 | 来源 | 是否必须 |
|--------|------|----------|
| sdd-context.md | `.sdd/sdd-context.md` | 是 |
| proposal.md | `openspec/changes/<change-name>/proposal.md` | 是 |
| design.md | `openspec/changes/<change-name>/design.md` | 是 |
| tasks.md | `openspec/changes/<change-name>/tasks.md` | 是 |

### 输出产物

| 输出项 | 路径 | 说明 |
|--------|------|------|
| review.md | `openspec/changes/<change-name>/review.md` | 评审记录（多轮追加） |
| sdd-context.md（更新） | `.sdd/sdd-context.md` | 阶段推进至 D4 或退回 D2 |
| D3产物 | `openspec/changes/<change-name>/review.md` | 记录到 sdd-context.md |

---

## 概述

> **Agent 路由提示**：本阶段由 **code-reviewer Agent** 主导，负责技术方案的审查和质量把关。

支持两种评审场景：
- **模式一：评审前自检** — 研发发起评审会前用，提前暴露问题（中等需求仅执行此模式）
- **模式二：评审会后记录** — 会议结束后记录结论和意见，形成追溯记录（大需求必须执行此模式）

评审结论三态：**通过 / 有条件通过 / 不通过**，驱动后续流程。

## Step 0：规模路由判断

读取 `.sdd/sdd-context.md` 中的 `需求规模` 字段，根据规模决定评审模式：

- **小需求**：提示"需求规模为小需求，跳过 D3 技术方案评审阶段"，直接更新 sdd-context.md 当前阶段为 D4，结束
- **中等需求**：自动进入模式一（评审前自检），完成后根据自检结果决定是否进入 D4
- **大需求**：展示模式选择菜单（Step 2），由用户选择评审模式

---

## Step 1：读取上下文和 OpenSpec artifacts

读取 `.sdd/sdd-context.md` 获取：需求编号、需求名称、需求规模、技术方案路径、执行人。

根据技术方案路径读取：

```
openspec/changes/<change-name>/proposal.md
openspec/changes/<change-name>/design.md
openspec/changes/<change-name>/tasks.md
```

若文件不存在，提示：

```
未找到 OpenSpec artifacts，请确认 D2 已完成。
技术方案路径：{技术方案路径}
```

读取完成后，若为中等需求直接进入模式一（Step M1），若为大需求进入 Step 2 选择评审模式。

## Step 2：选择评审模式

> 仅大需求展示此菜单，中等需求自动进入模式一。

```
请选择评审模式：
1. 评审前自检（我准备发起评审，先自查一遍）
2. 评审会后记录（评审会已结束，记录结论和意见）
```

---

## 模式一：评审前自检

### M1-Step 1：识别设计范围

读取 `design.md`，自动识别本次方案涉及的设计模块（后端/前端/DB/API/中间件/性能/安全），只对有内容的模块生成 checklist，无内容的跳过。

### M1-Step 2：逐项自检

**只展示 design.md 中有实际内容的模块**，无内容的模块直接跳过，不展示空 checklist。对每个展示的模块，逐项确认（Y/N/部分）：

**后端业务逻辑**
```
□ 业务边界是否清晰？边界外的情况是否有说明
□ 异常分支和错误场景是否都有处理方案
□ 涉及事务的操作是否明确了事务范围和回滚策略
□ 与其他服务/模块的依赖关系是否已确认
```

**数据库/表结构**
```
□ 新增字段是否有合理的默认值和 NOT NULL 约束
□ 索引设计是否覆盖主要查询场景，是否有冗余索引
□ 字段命名是否符合团队规范
□ 大表变更是否考虑了执行时间和锁表风险
```

**API 接口契约**
```
□ 接口是否满足幂等性要求（POST/PUT）
□ 请求参数是否有明确的校验规则
□ 错误码和错误信息是否统一规范
□ 接口版本和兼容性是否已考虑
```

**中间件/三方系统**
```
□ 消息队列的消费失败重试和死信队列是否有方案
□ Redis 缓存的过期策略、缓存穿透/击穿/雪崩是否有防护
□ 三方接口的超时、降级、熔断策略是否明确
```

**性能方案**
```
□ 高并发场景是否有压测预估或限流方案
□ 大数据量查询是否有分页或异步处理
□ 缓存策略是否合理，是否有缓存更新机制
```

**安全方案**
```
□ 接口权限控制是否完整（登录态、角色权限）
□ 用户输入是否有 SQL 注入防护
□ 敏感数据是否脱敏处理（日志、响应体）
□ 文件上传是否有类型和大小限制
```

**风险与待确认项**
```
□ design.md 中每条风险是否都有对应处理方案或说明
□ 待确认项是否已通过评审人或产品确认
```

### M1-Step 3：汇总自检结果

展示自检结果汇总，标出未通过或部分通过的项。

**若所有项均通过**，直接生成评审材料，不询问"是否修改"。

**若有未通过项**，询问：

```
自检发现 X 项需要关注，是否现在修改 design.md？
1. 是，我现在修改，修改完重新自检
2. 否，记录为待确认项，发起评审会时带上
```

选"是"→ 提示修改 `design.md` 后重新执行 D3 自检。
选"否"→ 将未通过项记录到 `review.md`，继续生成评审材料。

### M1-Step 4：生成评审材料

输出给评审人的评审材料摘要：

```markdown
## 评审材料 - {需求名称}

**需求编号**：{需求编号}
**需求规模**：{中等需求 / 大需求}
**提交人**：{执行人}
**评审时间**：待定

### 方案文件
- proposal.md：openspec/changes/{change-name}/proposal.md
- design.md：openspec/changes/{change-name}/design.md
- tasks.md：openspec/changes/{change-name}/tasks.md

### 自检结论
通过项：X / 全部
待确认项：（列出）

### 评审重点
> 根据 design.md 第11节风险与待确认项自动提取
```

### M1-Step 5：中等需求自检完成后的流程

**中等需求**：自检完成后，若无未通过项，直接视为评审通过，生成 `review.md` 记录自检结论，更新 sdd-context.md 推进至 D4。若有未通过项且用户选择"否（记录为待确认项）"，则视为有条件通过，同样推进至 D4，待确认项记录到 review.md 中供 D5 CR 确认。

## 模式二：评审会后记录

### M2-Step 1：录入评审基本信息

```
① 评审日期（直接回车取今天）
② 评审人（多人用逗号分隔）
③ 评审结论：
   1. 通过
   2. 有条件通过（有待跟踪项，可进入D4）
   3. 不通过（需修改后重新评审）
```

### M2-Step 2：录入评审意见

根据结论分支处理：

**结论为"通过"**：

```
请输入评审意见（可留空）：
```

**结论为"有条件通过"**：

```
请逐条录入待跟踪项（每条回车，全部输完后输入"完成"）：
格式：[优先级 高/中/低] 问题描述
示例：[高] 导出接口需要加限流，防止大数据量时拖垮数据库
```

**结论为"不通过"**：

```
请逐条录入需要修改的问题（每条回车，全部输完后输入"完成"）：
格式：[模块] 问题描述
示例：[DB设计] 订单表导出字段缺少索引，大数据量查询会超时
```

### M2-Step 3：生成 review.md

将评审记录写入：

```
openspec/changes/<change-name>/review.md
```

格式：

```markdown
# 技术方案评审记录 - {需求名称}

## 第 {N} 轮评审

**评审日期**：{日期}
**评审人**：{评审人列表}
**提交人**：{执行人}
**结论**：{通过 / 有条件通过 / 不通过}

### 评审意见

{评审意见内容}

### 待跟踪项（有条件通过时填写）

| 优先级 | 问题描述 | 状态 | 跟踪截止 |
|--------|----------|------|----------|
| 高     | ...      | 待处理 | D5 CR前 |

### 需修改项（不通过时填写）

| 模块 | 问题描述 | 状态 |
|------|----------|------|
| DB设计 | ... | 待修改 |
```

若 `review.md` 已存在（第二轮评审），追加新一轮记录，不覆盖历史。

## Step 3：根据结论推进流程

### 结论：通过 ✅

更新 `.sdd/sdd-context.md`（只修改以下字段，禁止写入其他内容）：

```
当前阶段: D4
D3产物: openspec/changes/{change-name}/review.md
```

输出进度块（按根 SKILL.md 的进度块规则，D1/D2/D3 标 ✅，D4 标 ▶️），然后输出：

```
✅ 技术方案评审通过
📋 评审记录：openspec/changes/{change-name}/review.md
直接说"继续"或"开始编码"即可。
```

### 结论：有条件通过 ⚠️

更新 `.sdd/sdd-context.md`（只修改以下字段，禁止写入其他内容）：

```
当前阶段: D4
D3产物: openspec/changes/{change-name}/review.md
```

输出进度块（D1/D2/D3 标 ✅，D4 标 ▶️），然后输出：

```
⚠️  技术方案有条件通过，以下待跟踪项需在 D5 Code Review 前确认：

{待跟踪项列表}

📋 评审记录：openspec/changes/{change-name}/review.md
直接说"继续"或"开始编码"即可。
提醒：D5 Code Review 时需确认以上待跟踪项已落实
```

### 结论：不通过 ❌

更新 `.sdd/sdd-context.md`（只修改以下字段，禁止写入其他内容）：

```
当前阶段: D2
D3产物: openspec/changes/{change-name}/review.md
```

输出：

```
❌ 技术方案评审不通过，需修改后重新评审

需修改项：
{需修改项列表}

📋 评审记录：openspec/changes/{change-name}/review.md
下一步：
1. 修改 OpenSpec artifacts（design.md / tasks.md）
2. 重新运行 sdd-d3-tech-review 进行第二轮评审
```

## 边界与注意事项

- review.md 只追加不覆盖，完整保留每轮评审历史
- 有条件通过的待跟踪项需携带到 D5 CR，D5 skill 会读取 review.md 确认落实情况
- 自检模式下 Claude 根据 design.md 内容动态生成 checklist，只检查有内容的模块
- 不通过时不能推进 D4，必须退回 D2 修改后重新过 D3
- 评审人字段尽量填写真实名字，形成可追溯的质量记录
- 小需求自动跳过 D3，不执行任何评审流程
- 中等需求仅执行 AI 自检模式，无需正式评审会，但自检结果仍需记录到 review.md
- 大需求必须执行正式评审会模式，保留完整的评审记录
