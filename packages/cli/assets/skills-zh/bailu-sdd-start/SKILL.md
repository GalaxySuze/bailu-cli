# Bailu SDD Start - 白鹿SDD研发阶段主入口

## 品牌信息

- **名称**：白鹿（Bailu）
- **前缀**：bailu:
- **寓意**：林深见鹿——在复杂的代码森林中，发现优雅的解决方案
- **理念**：在原生能力基础上叠加工作流规则

## 兼容入口说明

本 Skill 是白鹿 SDD（Specification-Driven Development）研发流程的主入口。同时提供 `/bailu-dev` 兼容入口：

- **SDD 可用时**：`/bailu-dev` 等同于 `/bailu-sdd-start`，自动进入 SDD 七阶段研发流程
- **SDD 不可用时**：`/bailu-dev` fallback 到白鹿原生四阶段工作流（需求讨论 → 方案文档 → AI Coding → 交付）

用户无需关心底层路由，只需使用熟悉的触发词即可。

## 概述

开发者唯一需要记住的入口。无论是开始新需求、还是继续已有需求，都从这里进入，自动路由到正确的阶段。

```
用户说"我要开发 DEMO-001" 或 "继续上次的需求"
         ↓
    bailu-sdd-start 环境预检
         ↓
    读取 .sdd/sdd-context.md
         ↓
    判断当前阶段
         ↓
    读取对应阶段 SKILL.md 并执行
```

## Pre-Check：专家团/多 Agent 模式检测

执行以下命令检测当前是否为多 Agent 并行模式：

```bash
echo "${QODER_AGENT_MODE:-standalone}"
```

- 输出为 `team` 或 `expert`：**立即停止**，输出以下提示，不执行任何后续步骤：

```
⚠️ 当前是多 Agent 并行模式，白鹿 SDD skill 套件不支持在此模式下运行。

SDD 流程依赖单一会话连续推进上下文，多 Agent 并行会导致
.sdd/sdd-context.md 状态不一致，阶段推进混乱。

请切换到普通会话模式后重新触发：
  /bailu-sdd-start 或 我要开发需求
```

- 输出为其他值（含 `standalone` 或命令不存在）：静默继续，不输出任何内容。

## Step 0.1：版本检查（每次必跑）

**每次 bailu-sdd-start 触发都执行此步**，不论是新需求还是续接/切换需求。

**仅对有 skill 目录的工具生效（Claude Code / Qoder / Trae），Cursor / Windsurf / Codex 跳过此步。**

v2 工作流通过 npm 包内 assets 分发，版本检查已迁移至 CLI 命令：

```
# 检查是否有新版本（不执行更新）
bailu update --check

# 更新到最新版本
bailu update
```

Skill 入口不做版本检查，由用户主动执行 `bailu update` 管理更新。

## Step 0：环境预检

首次进入（`.sdd/sdd-context.md` 不存在）时执行一次，已有上下文时跳过。

### Step 0.0：确认项目根目录

检测当前目录是否为业务工程根目录：

```bash
ls pom.xml package.json composer.json build.gradle go.mod requirements.txt 2>/dev/null | head -1
```

**有命中**：当前目录就是项目根目录，继续。

**无命中**：提示用户确认：

```
⚠️ 当前目录不像项目工程根目录：{pwd}

`.sdd/sdd-context.md` 需要建在业务项目根目录（`.sdd/` 目录）下，否则续接时会找不到上下文。

请告诉我你的项目根目录路径（如 ~/workspace/order-service），
或直接回车在当前目录继续：
```

用户输入路径后，校验路径存在且包含工程特征文件，确认后**后续所有文件读写使用该绝对路径**，不要求用户重新 cd 或重开对话。

若用户直接回车，在当前目录继续，不再提示。

### Step 0.2：其他环境检测

依次运行以下检测：

```bash
# 1. 检测 Git
command -v git &>/dev/null && git --version || echo "git_missing"

# 2. 检测 Git 用户名
git config user.name || echo "git_user_missing"

# 3. 检测 OpenSpec CLI（可选）
command -v openspec &>/dev/null && echo "openspec_available" || echo "openspec_missing"
```

根据结果处理：

| 检测项 | 结果 | 处理方式 |
|--------|------|---------|
| Git | 未安装 | 提示安装：macOS `brew install git` / Windows 安装 [Git for Windows](https://git-scm.com) / Linux `apt install git`，**阻塞，安装后继续** |
| Git 用户名 | 未配置 | 引导执行 `git config --global user.name "你的姓名"`，**阻塞，配置后继续** |
| OpenSpec CLI | 未安装 | 提示"未检测到 OpenSpec CLI，D2 将使用 AI 模式生成技术方案，效果一致"，**不阻塞，继续执行** |

预检通过后展示一次结果：

```
✅ 环境检测完成
Git：      已安装 (2.x.x)
Git 用户名：zhangsan
OpenSpec： 未安装（将使用 AI 模式）
```

然后执行：

```bash
mkdir -p .sdd
```

然后直接进入 Step 1，无需用户确认。

## Step 1：读取上下文

尝试读取 `.sdd/sdd-context.md`。

**文件存在且有当前阶段** → 续接已有需求，进入 Step 2 展示状态。

**文件不存在或需求编号为空** → 新需求，先从用户的触发消息中提取信息：

**提取规则**（优先从触发消息中读取，能提取到就不询问）：

| 字段 | 提取方式 |
|------|---------|
| 需求编号 | 触发消息中形如 `DEMO-XXXX` 的编号 |
| 需求名称 | 触发消息中编号之后的自然语言描述 |
| 需求文档路径 | 触发消息中包含路径特征的字符串（如 `/`、`.md`、`.doc`、`http`） |

**提取后的处理逻辑**：

- **三项都有**：直接进入规模推荐，不询问
- **有编号 + 有描述，无文档路径**：直接进入规模推荐，文档路径留空
- **只有编号，无描述**：仅询问 ② 需求名称或描述，不询问其他
- **三项都没有（裸触发）**：询问全部三项：

```
未找到当前研发上下文，开始一个新需求。

① 需求编号（如 DEMO-001，没有可留空）：
② 需求名称或简要描述：
③ 需求文档或原型路径（可先跳过，直接回车）：
```

收集后，根据需求描述做一次智能分析，给出带理由的规模推荐：

**分析规则**（内部判断，不展示给用户）：

| 信号特征 | 推荐规模 |
|---------|---------|
| "加一个"、"改一下"、纯前端样式、无接口变更、单一功能点 | 小需求 |
| 有接口新增/变更、前后端协作、涉及多个模块、有 DB 改动 | 中等需求 |
| 新建系统/子系统、跨团队协作、改动量大、明确提到需要评审 | 大需求 |
| 描述模糊、范围不清晰 | 中等需求（保守推荐） |

展示格式（三个选项必须完整输出，禁止省略任何一行）：

```
根据需求「{需求名称}」分析：
- {分析点1，如：涉及后端接口 + 前端改动}
- {分析点2，如：有新增接口，需要技术方案}

建议规模：{推荐规模} ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 小需求（快速模式）
   适合：改一两个功能点，改动范围清晰，无需跨模块协作
   流程：拆任务 → 写代码（动手前会话内确认改动范围）→ 代码检查+自测
   预计：1~2 轮对话

2. 中等需求（标准模式）
   适合：多模块改动，有前后端协作，需要技术方案
   流程：拆任务 → 出方案 → AI自检 → 写代码 → CR → 测试缺陷闭环 → 上线发版
   预计：3~5 轮对话

3. 大需求（完整模式）
   适合：功能复杂、改动量大、需要正式评审会（需约人）
   流程：拆任务 → 出方案 → 正式评审会 → 写代码 → CR → 测试缺陷闭环 → 上线发版
   预计：多天多轮对话
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

直接回车选推荐的{推荐规模}，或输入 1 / 2 / 3 切换：
```

**注意：以上三个选项的「适合」、「流程」、「预计」三行必须完整展示，不得因为排版或简洁原因省略。**

将用户选择记录到 `.sdd/sdd-context.md` 的 `需求规模` 字段，路由阶段时按规模决定跳过/合并哪些阶段。

从 ① 需求编号 + ② 需求名称派生 change-name（kebab-case）：
- 有编号：`DEMO-001-order-list-excel-export`
- 无编号：`order-list-excel-export`

将 change-name 写入 `.sdd/sdd-context.md` 的 `change-name` 字段，后续所有阶段使用此值，不重复询问。

## sdd-context.md 格式规范（严格遵守）

`sdd-context.md` 是状态索引文件，**只允许包含以下固定字段，禁止写入需求背景、方案描述、任务清单或任何其他内容**：

```yaml
需求编号: DEMO-001
需求名称: 订单列表 Excel 导出
change-name: DEMO-001-order-list-excel-export
需求规模: 中等需求
当前阶段: D4
当前分支: develop-20260528-task-DEMO-001-zhangsan
技术方案路径: openspec/changes/DEMO-001-order-list-excel-export/design.md
SP总计: 4
执行人: zhangsan
工程名: order-service
开始日期: 2026-05-28
阶段产物索引:
  D1: openspec/changes/DEMO-001-order-list-excel-export/tasks.md
  D2: openspec/changes/DEMO-001-order-list-excel-export/design.md
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| 需求编号 | 需求唯一标识，如 DEMO-001，无编号可留空 |
| 需求名称 | 需求的简要描述 |
| change-name | kebab-case 格式的唯一标识，从需求编号+名称派生，用于目录命名和文件路径 |
| 需求规模 | 小需求 / 中等需求 / 大需求，决定阶段跳过策略 |
| 当前阶段 | D1-D7 之一，或"完成"，表示当前推进到的阶段 |
| 当前分支 | 当前开发分支名 |
| 技术方案路径 | 技术方案文档的相对路径 |
| SP总计 | Story Points 总计 |
| 执行人 | 当前开发者 Git 用户名 |
| 工程名 | 工程/项目名称 |
| 开始日期 | 需求开始日期 |
| 阶段产物索引 | 各阶段产物的文件路径，每个阶段完成后追加一行，格式 `DX: 相对路径` |

- 需求背景、技术方案、任务清单等内容写入 `openspec/changes/{change-name}/` 目录下对应文件
- 每次更新只修改变化的字段，不重写整个文件
- 字段未知时留空，不填占位文字
- `阶段产物索引` 字段在每个阶段完成后由对应阶段 Skill 追加，用于快速定位各阶段产出

## 白鹿 Agent 路由

各阶段自动路由到对应的白鹿 Agent，确保每个阶段由最合适的专业 Agent 执行：

| 阶段 | 路由 Agent | 说明 |
|------|-----------|------|
| D1 任务分配与评估 | **planner** | 负责任务拆分、SP 估算和规划 |
| D2 技术方案设计 | **architect** | 负责系统架构和技术方案设计 |
| D3 技术方案评审 | **code-reviewer** | 负责方案评审和 AI 自检 |
| D4 开发编码 | **backend-developer** / **frontend-developer** | 根据任务类型选择后端或前端 Agent |
| D5 代码评审 | **code-reviewer** | 负责代码审查 |
| D6 测试与缺陷闭环 | **test-engineer** | 负责测试用例和缺陷管理 |
| D7 上线/发版 | **code-reviewer** | 负责上线前检查和 MR 审查 |

Agent 路由为推荐策略，具体执行时可根据实际任务类型灵活调整。

## Step 3：阶段路由

根据 `.sdd/sdd-context.md` 中的**当前阶段**和**需求规模**，决定执行路径。

### 小需求路由

| 当前阶段 | 执行方式 |
|----------|---------|
| D1       | 读取 `bailu-sdd-d1-planning/SKILL.md`，完成后**直接跳过 D2/D3，推进 D4**，并输出完整路线图（流程预览） |
| D2       | 跳过，不读取，不生成任何 OpenSpec 文件 |
| D3       | 跳过 |
| D4       | 读取 `bailu-sdd-d4-coding/SKILL.md`，进入**小需求模式**：扫代码 → 会话内输出改动范围确认 → 用户确认后直接写代码，完成后进入 D5 |
| D5       | 读取 `bailu-sdd-d5-code-review/SKILL.md`，完成后**直接进入 D6** |
| D6       | 读取 `bailu-sdd-d6-test-closure/SKILL.md`，完成测试与缺陷闭环后进入 D7 |

## Step 4：异常情况处理

### 阶段回退（如 D3 不通过退回 D2）

`.sdd/sdd-context.md` 中当前阶段已被对应阶段自动更新，下次进入时会自动路由到退回的阶段，无需额外处理。

### 上下文字段不完整

若 `.sdd/sdd-context.md` 存在但关键字段（需求编号、当前阶段）为空，询问补充后继续，不强制重新走 D1。

### 多需求并行与切换

项目目录下维护一个 `.sdd/` 归档目录，存放所有暂停中和已完成的需求上下文：

```
项目根目录/
└── .sdd/
    ├── sdd-context.md                      ← 当前活跃需求
    ├── DEMO-001-order-list-export.md     ← 暂停中（阶段字段 = D4）
    ├── DEMO-003-user-auth.md             ← 已完成（阶段字段 = 完成）
    └── payment-refund.md                   ← 无编号需求
```

**切换需求时**：

1. 将当前 `.sdd/sdd-context.md` 内容保存到 `.sdd/<change-name>.md`
2. 检查 `.sdd/` 下是否有目标需求文件：
   - 有 → 加载该文件内容到 `.sdd/sdd-context.md`，从中断处续接
   - 无 → 当作新需求，走 Step 1 收集信息
3. 展示切换结果

用户说"切换到 DEMO-001"或"继续订单导出需求"时触发切换。

**查看所有需求状态**：

用户说"查看所有需求"或"有哪些进行中的需求"时，列出 `.sdd/` 下所有文件及状态：

```
📋 需求列表

进行中：
  DEMO-001-order-list-export（D4 开发编码）

已完成：
  DEMO-003-user-auth（完成）

当前活跃：payment-refund（D2 技术方案设计）
```

## 边界与注意事项

- 本文件是套件唯一自动触发入口，D1-D7 子文件通过 Read 工具按需加载执行
- 每个阶段执行完毕后负责更新 `.sdd/sdd-context.md` 的当前阶段，并在 `阶段产物索引` 中追加产物路径，下次进入自动续接
- D1 完成后自动输出完整路线图（流程预览），帮助开发者了解后续各阶段的产出和模式
- 不强制阶段顺序检查，研发可以从任意阶段进入，但各阶段内部会做前置检查
- 严禁在任何研发阶段提出合并代码到 master 的建议，代码合并由团队 Git 管理流程处理
- 任务管理工具 对接为选填项：个人开发可跳过，团队协作任务可在 D1 任务清单生成后手动对接 任务管理工具
- `/bailu-dev` 命令在 SDD 可用时等同于 `/bailu-sdd-start`，否则自动 fallback 到白鹿原生四阶段工作流
