# SDD D6 - 测试与缺陷闭环

## 概述

D6 是上线前的测试与缺陷闭环阶段，可调用专门测试 skill 完成测试验证，覆盖四个环节：

1. **单元测试** — 核心业务逻辑的自动化验证
2. **本地功能自测** — 按需求验收标准逐项验证
3. **前后端联调** — 前后端接口协议对齐和联合调试
4. **三方接口联调** — 与外部系统/接口的对接验证

**D6 测试发现的问题在 D6 内修复闭环，不再单独进入 D7。**
D7 是可选的上线/发版辅助阶段，负责 AI 辅助创建 Merge Request。

## 白鹿 Agent 路由

D6 测试阶段可路由到白鹿 `test-engineer` Agent 进行系统化的测试执行。Agent 会根据项目类型和测试范围自动生成测试用例、执行测试、收集结果并完成缺陷闭环。

路由方式：
- 自动检测到 D6 阶段时，提示用户是否启用 `test-engineer` Agent
- 用户也可主动说"用 test-engineer 测试"来触发 Agent 路由

## 阶段入口契约

### 前置条件

进入 D6 测试与缺陷闭环阶段前，必须满足以下条件：

1. 当前阶段 = `D6`（读取 `.sdd/sdd-context.md` 确认）
2. D5 代码评审已通过（AI 审核 + 人工审核均已通过）

### 输入产物

- `.sdd/sdd-context.md` — SDD 上下文
- `openspec/changes/<change-name>/tasks.md` — 任务清单（确认全部完成）
- `openspec/changes/<change-name>/design.md` — 技术设计方案（获取接口契约和功能范围）
- `openspec/changes/<change-name>/review.md` — D3 待跟踪项和 D5 CR 问题

## Step 1：读取上下文

读取 `.sdd/sdd-context.md`，确认当前阶段为 D6。

若不是 D6，停止并提示先完成前置阶段。

读取：
- `openspec/changes/<change-name>/tasks.md` — 确认所有任务已完成
- `openspec/changes/<change-name>/design.md` — 获取接口契约和功能范围
- `openspec/changes/<change-name>/review.md` — 获取 D3 待跟踪项和 D5 CR 问题

输出本次测试范围摘要，直接进入 Step 2。

## Step 2：确认测试范围

询问本次涉及哪些联调对象（可多选）：

```
本次需要进行哪些测试和联调？（输入序号，多个逗号分隔，直接回车全选）

1. 单元测试
2. 本地功能自测
3. 前后端联调
4. 三方接口联调
```

根据选择只执行对应环节，其余标注"不涉及"。若当前项目存在专门测试 skill，优先调用测试 skill 完成测试用例生成、执行和结果汇总；D6 负责承接测试结果并完成缺陷闭环。

**执行原则：AI 先测，人工补充确认。** D6 不得默认把测试 checklist 全量交给用户手测；必须先由 AI 执行所有可自动化、可命令行验证、可浏览器观察的测试项，再把 AI 无法可靠判断的业务确认、视觉体验、真实账号/权限、外部环境限制项交给用户人工确认。

- 命令行可验证项：AI 直接运行测试、构建、类型检查、lint 或项目约定的验证命令。
- 接口可验证项：AI 使用现有测试、curl/HTTP 客户端、Mock/沙箱环境或项目脚本验证请求、响应和错误场景。
- Web/UI 可验证项：若本地应用可启动或已运行，AI 优先使用浏览器自动化、截图观察或可用的验证 skill 打开页面、点击交互、检查 DOM/文本/状态变化、验证主题切换和响应式表现。
- 仅当存在登录凭据、验证码、真实业务判断、肉眼审美确认、外部系统权限等 AI 无法完成的限制时，才要求用户人工协助，并说明哪些项 AI 已测、哪些项需要人工确认、为什么需要人工。

## 环节一：单元测试

### 执行测试

根据项目类型自动尝试运行单元测试：

```bash
# Java
mvn test -q 2>/dev/null || ./gradlew test 2>/dev/null

# PHP
php artisan test 2>/dev/null || ./vendor/bin/phpunit 2>/dev/null

# Python
pytest 2>/dev/null || python -m pytest 2>/dev/null

# React
npm test -- --watchAll=false 2>/dev/null
```

若无法识别，询问用户提供测试命令。

### 测试结果处理

**全部通过**：记录通过，继续下一环节。

**有失败**：

```
以下测试用例失败：
{失败列表 + 错误信息}

是否现在修复？
1. 是，AI 分析并修复
2. 否，记录为测试问题，我稍后处理
```

选"是"→ AI 分析失败原因，修复代码，重新运行测试，直到全部通过。
选"否"→ 记录到测试缺陷清单，继续后续环节，D6 结束前必须全部处理。

### 覆盖率检查

若项目有覆盖率配置，输出当前核心模块的覆盖率，低于 60% 给出提示，不强制阻塞。

## 环节二：本地功能自测

### 生成并执行验收 Checklist

基于 `design.md` 的功能范围和 `proposal.md` 的需求背景，自动生成功能验收 checklist，并按"AI 可执行项"和"需人工确认项"拆分：

```markdown
## 功能自测 Checklist - {需求名称}

### AI 自动/半自动验证项
- [ ] {功能点1} — 验证方式：{命令/接口/浏览器操作} — 预期结果：{...}
- [ ] {功能点2} — 验证方式：{命令/接口/浏览器操作} — 预期结果：{...}

### 需人工确认项
- [ ] {确认点1} — 需要人工原因：{如真实账号/权限/视觉审美/外部系统限制}

### 异常场景
- [ ] {异常场景1} — 验证方式：{...} — 预期结果：{错误提示/降级行为}
- [ ] {异常场景2} — 验证方式：{...} — 预期结果：{...}

### 边界场景
- [ ] {边界场景1} — 验证方式：{...} — 如：空列表、超大数据量、特殊字符
```

AI 先逐项执行"AI 自动/半自动验证项"，并输出每项的实际操作、观察结果和结论。若 Web/UI 应用可访问，必须优先打开页面实际操作验证，不得只列出人工测试步骤。

仅对"需人工确认项"请求用户反馈：

```
AI 已完成以下验证：
{AI 验证项 + 结论 + 关键证据}

以下项目因 {限制原因} 需要你人工确认：
{需人工确认项列表}

请逐项确认（输入序号+结果，如 "1 通过"、"2 失败:具体现象"），或直接回车表示这些人工确认项全部通过。
```

### 问题处理

发现失败项：

```
功能自测发现问题：
{问题描述 + 现象}

AI 分析原因并修复，修复完成后重新验证此项。
```

修复后标记该项通过，继续。

## 环节三：前后端联调

### 接口逐条联调

从 `design.md` 提取接口列表，逐条确认联调结果：

```
接口联调清单：

1. POST /api/order/export — 订单导出
   预期：返回 Excel 文件，状态码 200
   联调结果：[ 通过 / 失败 ]

2. ...
```

研发逐条回报：

- **通过**：记录通过
- **失败**：描述现象，AI 分析是前端问题、后端问题还是协议不一致，给出修复建议，修复后重新联调

### 联调记录

记录每条接口的联调时间、结论、发现的问题和修复情况。

---

## 环节四：三方接口联调

### 识别三方依赖

从 `design.md` 提取三方系统/接口列表，询问当前联调环境：

```
本次涉及以下三方系统：
{三方系统列表}

当前联调环境：
1. Mock/沙箱环境
2. 真实测试环境
3. 直连生产（需谨慎）
```

### 联调验证

逐个三方接口确认：

```
三方接口联调：

1. {三方名称} - {接口描述}
   联调结论：[ 通过 / 失败 / 待联调（对方环境未就绪） ]
   备注：{...}
```

**失败时**：AI 分析是参数问题、鉴权问题还是对方服务问题，给出排查建议。

**待联调（对方未就绪）**：记录为阻塞项，标注对方联系人和预计就绪时间，不阻塞当前 D6，但推进 D7 前必须完成。

---

## Step 3：汇总测试缺陷清单

所有环节结束后，汇总发现的所有问题及处理情况：

```markdown
## D6 测试缺陷清单

| 序号 | 环节 | 问题描述 | 严重程度 | 状态 |
|------|------|----------|----------|------|
| 1    | 功能自测 | 导出空数据时报500 | 高 | 已修复 |
| 2    | 三方联调 | 支付回调待联调 | 中 | 阻塞中 |
```

若有未解决的问题，不允许推进 D7，必须全部处理或标注为"外部阻塞（三方未就绪）"。超出当前需求范围、历史遗留问题或需要产品决策的问题，不在 D6 强行修复，应记录为风险或新缺陷。

## Step 4：更新 SDD 上下文并推进

所有问题处理完成后，将测试记录追加到：

```
openspec/changes/<change-name>/review.md
```

格式：

```markdown
### D6 测试与缺陷闭环记录

**日期**：{日期}
**执行人**：{执行人}

| 环节 | 结论 | 问题数 | 已修复 |
|------|------|--------|--------|
| 单元测试 | 通过 | 0 | — |
| 功能自测 | 通过 | 2 | 2 |
| 前后端联调 | 通过 | 1 | 1 |
| 三方联调 | 通过 | 0 | — |
```

更新 `.sdd/sdd-context.md`（只修改以下字段，禁止写入其他内容）：

```
当前阶段: D7
```

输出进度块（按根 SKILL.md 的进度块规则，D1-D6 标 ✅，D7 标 ▶️ 可选），然后输出：

```
✅ D6 测试与缺陷闭环完成

单元测试：通过
功能自测：通过（发现 {X} 个问题，已全部修复）
前后端联调：通过
三方联调：通过

需求已可交付。

如需 AI 辅助执行上线前检查、创建 Merge Request，说"D7"或"发版"即可。
也可以跳过 D7，直接手动合并分支，需求研发阶段即告完成。
```

## 边界与注意事项

- D6 测试发现的问题必须在 D6 内修复，不得带着当前需求范围内的已知 bug 推进
- 三方接口"对方未就绪"是合法的外部阻塞，可带此状态推进，但推进 D7 前必须完成
- 测试 checklist 基于 design.md 自动生成，若需求有未在 design.md 体现的验收标准，用户可补充
- D6 可以承接研发自测、QA/UAT 反馈和专门测试 skill 的结果，统一完成缺陷闭环；D7 是可选的上线辅助阶段
